# Django ORM Migration Rules

> These rules apply to projects that use Django ORM.
> All developers and agents MUST follow these rules.

---

## Prohibitions

### `manage.py flush` is FORBIDDEN

Deletes data in all tables (table structures are preserved).

**Why:** Irreversible data loss. Even if table structure is preserved, contents are fully deleted.

**Correct alternative:** Use the Django ORM or shell to delete specific data.

### `manage.py reset_db` is FORBIDDEN

Completely deletes and recreates the database (django-extensions).

**Why:** All schema and data are lost.

**Correct alternative:** To roll back a specific app's migrations: `python manage.py migrate <app> zero`

---

## Forbidden Commands Table

| Command | Why | Alternative |
|-------|-------|------------|
| `manage.py flush` | Deletes all data | Delete specific data via ORM |
| `manage.py reset_db` | Fully resets the DB | `migrate <app> zero` |
| `manage.py migrate --fake` | Marks migration as applied without running | Use carefully; verify DB state |

## Migration Creation Flow

```
Make model change (models.py)
        |
python manage.py makemigrations
        |
Inspect generated migration file
        |
python manage.py migrate
        |
If destructive change exists:
        | (if destructive change exists)
Plan data backup + confirm with user
        |
Update application code (views, serializers, forms, etc.)
        |
Run tests: python manage.py test
        |
Commit (models.py + migration file TOGETHER)
```

**NEVER** change a model and leave it without running `makemigrations`.

---

## Migration Types

### Schema Migration (Automatic)
Migrations auto-generated by `makemigrations`. Reflect model changes to the database.

### Data Migration (Manual)
Create an empty migration with `python manage.py makemigrations --empty <app>` and write data manipulation by hand.

```python
from django.db import migrations

def populate_data(apps, schema_editor):
    MyModel = apps.get_model('myapp', 'MyModel')
    # Data manipulation...

class Migration(migrations.Migration):
    dependencies = [('myapp', '0005_auto')]
    operations = [
        migrations.RunPython(populate_data, migrations.RunPython.noop),
    ]
```

**Rule:** Data migrations must provide a reverse function with `RunPython.noop` at minimum.

## Migration Risk Table

| Change | Risk | Action |
|-----------|------|---------|
| New model (table) | Low | Normal flow |
| New nullable field | Low | Normal flow |
| New NOT NULL field (with default) | Medium | Check existing data |
| `RemoveField` | Critical | Notify the user |
| `DeleteModel` | Critical | NEVER do automatically |
| `RenameField` | High | Data loss risk; all references must be updated |
| `RenameModel` | High | All imports and references must be updated |
| `AlterField` (type change) | Medium | Data truncation/conversion error |
| `AlterUniqueTogether` | Medium | Verify uniqueness of existing data |
| `AlterIndexTogether` | Low | Performance may be affected |
| `RunSQL` (raw SQL) | High | Content must be inspected carefully |
| `RunPython` (data migration) | Medium | Reverse function must be provided |

## Squash Migration

Long migration chains can be squashed for performance:

```bash
python manage.py squashmigrations <app> <start> <end>
```

**Rules:**
- After squash, do not delete old migration files immediately — wait until everyone on the team has moved to the new migration.
- Migrations containing `RunPython` and `RunSQL` must be squashed carefully.
- After squash, verify with `python manage.py migrate`.

---

## Mandatory Rules

1. **Model change + migration are committed TOGETHER.** A `models.py` change cannot be committed without a migration file.
2. **Every migration is inspected.** Do not blindly commit `makemigrations` output.
3. **Data backup is REQUIRED for destructive migrations.** Create a backup plan before migrations that contain `RemoveField` or `DeleteModel`.
4. **Data migrations provide a reverse path.** Written as `RunPython(forward, reverse)`.
5. **Avoid circular dependencies.** Use the `app_label.ModelName` string format for `ForeignKey` relations.
6. **Migration files are not edited by hand** (except when required). Re-run `makemigrations`.
7. **Verify DB state before using `--fake`.** Incorrect `--fake` usage causes schema mismatch.
